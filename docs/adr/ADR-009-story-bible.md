# ADR-009：设定库——AI 抽取候选，作者确认后入库
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 设定一致性和角色一致性检查都需要一个检查基准。
- 用户选择让 AI 从正文中自动抽取设定，由作者确认后入库。
- 长篇小说中，很多属性会随剧情变化，比如境界、所在位置、伤势。不能简单地把「前后不一致」都判为错误。

## 候选选项 (Options)
1. **抽取结果直接入库**
   - 缺点：模型的错误会污染检查基准，导致误报越来越多。
2. **抽取结果作为候选，由作者审核后入库**
   - 优点：基准可信。
   - 缺点：需要作者花时间审核。
3. **构建知识图谱或向量库（参考 NovelCanon）**
   - 优点：能力强。
   - 缺点：v1 不需要，复杂度高（YAGNI）。

## 决定 (Decision)
采用选项 2。

**数据结构**
- 设定库由条目（`bible_entry`）和事实（`bible_fact`）组成。
- 条目类型：角色、地点、势力、物品、规则、其他。
- 条目有名称和别名，名称和别名不能重复（INV-9）。
- 每条事实记录以下信息：
  - `attribute`（属性）、`value`（值）；
  - `mutable`：这个属性是否会随剧情变化；
  - 来源章节 `chapter_id`；
  - 逐字引用 `quote`（INV-8）。

**抽取与审核流程**
- 抽取任务逐章执行，结果按章节正文的 `body_hash` 缓存。
- 本地按名称和别名把抽取结果与已有条目匹配，生成三类候选：`new_entry`（新条目）、`new_fact`（新事实）、`new_alias`（新别名）。
- 候选的引用必须是原文的逐字内容，否则丢弃。
- 作者对候选可以：接受、编辑后接受、合并到已有条目、拒绝。

**用于一致性检查时**
- 只提供本块中出现的条目。
- 不变的事实全部提供。
- 可变的事实只提供「截至上一章的最新值」，并标注来自哪一章。
- 模型据此区分「合理的剧情变化」和「前后矛盾」。

## 理由 (Rationale)
- 作者确认是检查基准可信的前提，否则一致性检查会出现「拿错的设定去查对的正文」的情况。
- 区分可变和不变、记录来源章节，借鉴了 NovelCanon 的「世界状态时间轴」思路，但简化成「截至某章」这一个维度，满足长篇连载的需要。

## 后果 (Consequences)
- **正面**
  - 设定库本身就是一份可编辑的「人物与设定手册」，作者可以直接查看和使用。
  - 设定库中的专名同时作为错别字检查的白名单，减少把人名、地名误判为错字。
- **负面 / 代价**
  - 第一次对百万字作品做抽取，会产生大量候选。为此提供：
    - 批量接受；
    - 按条目分组；
    - 按出现次数排序。
  - 别名合并依赖作者判断；v1 不做自动的实体聚类。

## 实施补充（2026-10-10，T16）

不改变上述决定，只记录实施中确定的细节（完整约定见 ARCHITECTURE F5、§7.2、§7.4.1）：
- **拒绝是持久的**：被拒绝的候选（按「新条目名称 / 目标条目 + 属性 + 值 / 目标条目 + 别名」的键）以后不再生成，否则每次改稿重新抽取都要再拒绝一遍。
- **同名的一组可以一次接受**：跨章节出现的同一新实体是多条候选；同一批审核中，后面的候选与前面刚新建的条目同名时自动合并进去。与审核前就存在的条目同名时仍然报冲突（409 `NAME_CONFLICT`），由作者决定合并——那可能确实是两个同名的人。
- **同一份输出里的实体先合并**：模型常把「小林」与「林远（又名小林）」分开输出，按名称与别名先合并，再匹配已有条目。
- **实体必须在正文中出现**：名称与别名都没在本章出现的实体丢弃，与引文校验（INV-8）一起防止模型编造。
- **抽取缓存按正文版本、全部片段完成才生效**：有片段失败的章节下次整章重新抽取，已有的候选按键去重，不会重复。
- **「截至上一章」取严格早于本章的来源**：本章自己写到的变化不算前情，否则模型无法发现本章内部与前文的矛盾。前文提及取第一次与最近一次出现，分别提供来历与最新状态。
