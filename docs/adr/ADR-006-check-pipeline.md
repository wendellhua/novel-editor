# ADR-006：AI 检查流程——模型只报告问题，本地锚定、过滤后修正
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 规模：百万字的作品无法一次性交给模型，必须分块检查，再把结果汇总。
- 模型能力：单靠大模型做中文拼写纠错效果不理想，容易过度修正（F7，ACL 2025）；而且模型给出的字符偏移量不可靠。
- 修正要求：一键修正必须精确，不能改坏原文。
- 能力需求：
  - 一致性检查要知道「前文写过什么」；
  - 审稿要能给出整体意见。

## 候选选项 (Options)
1. **让模型改写整段，再用 diff 找出修改**
   - 缺点：模型会顺手改动其他内容，diff 噪声大，无法逐条采纳。
2. **让模型返回字符偏移量**
   - 缺点：模型数不准字数，定位会错位。
3. **让模型返回原文逐字片段 `excerpt` 和问题文字 `target`，由本地程序定位并过滤**
   - 优点：定位可验证；可以逐条采纳或忽略；能用本地规则压制误报。
   - 缺点：片段不唯一或模型改写了原文时，会丢弃少量结果。
4. **接入本地 BERT 类纠错小模型**
   - 缺点：需要 Python 或原生运行时，违反打包约束。

## 决定 (Decision)
采用选项 3，细节见 ARCHITECTURE §3.3 F3/F4、§7.4。

**分块方式**
- 一个任务 = 若干执行单元，单元分为 `summary`、`main`、`reduce` 三个阶段。
- `main` 阶段按章切分，章内再按段落边界切块，块大小见 `CHUNK_CHARS`。

**上下文供给**：一致性检查不是把全书交给模型，而是只提供以下三类内容：
- 设定库中本块出现的条目和事实；
- 前 3 章的摘要；
- 用 FTS 找到的前文提及片段。

**锚定**：模型返回 `excerpt`（8～40 个字）和 `target`。本地按以下顺序查找：精确匹配 → 归一化后匹配 → 匹配失败则丢弃。

**过滤**（INV-10）：错别字类问题限制长度和长度差，并且不允许命中设定库中的专有名词。

**修正**：按以下顺序执行：
1. 保存当前章节；
2. 校验或重新锚定问题位置；
3. 去掉相互重叠的修改；
4. 生成 `before_fix` 版本；
5. 从后往前替换；
6. `rev` 加 1。

**缓存**：
- `chapter_analysis` 以 `body_hash` 为键缓存每章摘要和抽取结果；
- 勾选 `onlyChanged` 时，跳过上一次同类检查后没有改动的章节。

**任务控制**：任务和执行单元都持久化保存，可以暂停、恢复、取消；重启后，原来在运行的任务变为 `paused`。

## 理由 (Rationale)
- 「片段锚定 + 逐字校验」让每条问题都能核对、能撤销，对应「AI 检查准确性」这一质量属性。
- 每次修正前写入快照，保证 AI 不会造成不可逆的丢稿，对应最高优先级的「不丢稿」。
- 摘要缓存和按需检查改动章节，可以把百万字作品的重复检查成本降到最低。

## 后果 (Consequences)
- **正面**
  - 检查结果可以审计、逐条采纳。
  - 换模型或换技能都不影响定位与修正逻辑。
  - token 成本可以预估、可以统计。
- **负面 / 代价**
  - 模型漏报的问题无法补救。
  - 原文片段不唯一时，非错别字类问题只取第一次出现的位置。
  - 一致性检查的效果依赖设定库的质量，所以首次使用前应先运行一次「设定抽取」。
  - 摘要阶段会额外消耗 token：约为正文的 1 倍输入和 2% 输出，只在首次运行和章节改动后产生。

## 实施补充（2026-10-10，T13）

不改变上述决定，只记录任务引擎实施中确定的细节（完整约定见 ARCHITECTURE §3.3 F3、§7.2、§7.4）：
- **单元提交是原子的**：模型结果写入、单元状态、任务计数与用量在同一个事务里提交。暂停、取消或进程被杀时，已提交的单元不会重复执行，未提交的单元下次重新执行，结果不会写两遍——这是「恢复时跳过已完成的单元」成立的前提。
- **两级失败**：与单元内容有关的失败（输出两次都不合格、截断、空内容、400 / 413 / 422）只让该单元失败，任务继续；与单元无关的失败（鉴权、额度、限流与 5xx 重试耗尽、超时、网络）让整个任务失败并保留进度，修好后恢复。为了不让「模型名写错」这类整体问题把每个单元都标成失败，一次运行中 0 成功且连续 3 个单元失败也判为任务失败。恢复时失败的单元重新执行。
- **重启修正按需进行**：任务数据存在各作品库里，进程被杀后不在启动时打开全部作品扫描（会拖慢启动），而是在本进程第一次访问某作品的任务时，把遗留的 queued / running 改为 paused。
- **检查期间改稿**：单元执行前比对章节 `body_hash`，变了就按当前正文重新切分该章尚未执行的部分；提示词与锚定使用同一份正文快照，问题记录快照的哈希，之后由重新锚定（INV-7）处理位置漂移。
- **类型逐步启用**：任务类型由处理器注册表驱动，`ENABLED_JOB_TYPES` 与注册表一致（加载期校验）。T13 只启用错别字检查，其余类型在 T15～T17 补上处理器后启用，期间界面显示「即将提供」。

## 实施补充（2026-10-10，T14）

- **锚定算法前后端共用**（`shared/anchor.ts`）：编辑器里可能有尚未保存的改动，高亮要在本地正文上定位，必须用与服务端完全相同的算法，否则同一处问题在两边位置不同。
- **修正后平移同章其余问题**：excerpt 有 8～40 字，常常覆盖到旁边的错字；只靠下次读取时按 excerpt 重新锚定，采纳一处就会让相邻的问题失效。修正事务里按替换的长度差平移不重叠的问题、重新截取 excerpt，重叠的才交给重新锚定。
- **去重覆盖其他任务**：同一章重复检查时，其他任务中仍待处理或已忽略的问题参与去重，作者的「忽略」因此是持久的；「已忽略」的问题也随正文重新锚定，以便下次检查时还能认出它。
- **撤销走编辑器历史**：修正结果作为单独一步历史记录写入编辑器，Ctrl/Cmd+Z 撤销后照常保存；服务端另有 before_fix 版本兜底。问题状态不随撤销回退（撤销表示作者不接受这次修改，不需要再次提示）。

## 实施补充（2026-10-10，T15）

- **摘要缓存按正文版本凑齐再生效**：长章节的摘要分片段生成，片段可能并发、乱序完成；只有同一正文版本的全部片段到齐才合并为有效缓存，之前的完整摘要继续供前情提要使用。这样第二次运行能可靠地命中缓存，改了哪章只重算哪章。
- **汇总一定放进预算**：审稿汇总的输入随章节数线性增长，不能交给通用的 ⑤→④→③ 裁剪（⑥ 不可裁剪）；由处理器按 ⑥ 的预算给每章同一个上限截断，章节极多时保留前面的章节并注明省略。层级汇总（先按卷汇总再汇总全书）留待需要时再做。
- **没有材料就不调用模型**：处理器可以声明跳过，避免为空输入付费、也避免模型编造报告。
- **报告渲染不引入库**：报告只需要标题、列表、段落与加粗；结构化解析 + 文本节点渲染从根上排除了 HTML 注入，不需要额外的消毒库。

## 补充 2（2026-10-13，交付后优化：AI 修复）

背景：审稿意见与部分一致性问题只有意见、没有可直接替换的建议，作者需要逐条手改。新增「修复」「全部修复」，由模型按意见改写。

决定：不改变「模型只报告问题、正文只经一键修正写入」的原则，AI 修复拆成两步：
- **第一步只生成建议**（`POST W/issues/:iid/suggest`）：模型只拿到这一处 `target`、它的意见与依据、前后文，输出放回原处的文字，写入问题的 `replacement`，不碰正文。改写的范围被锁在 `target` 上，模型改不到别处。
- **本地整理与限长**：模型常把前后文一起输出、自己加引号或句号；整理掉与前后文重复的部分，与原文相同或超过 `max(200, target × 4)` 的不采用。
- **第二步照常一键修正**：与已有建议一起走 `apply`——先保存、对齐、`before_fix` 版本、编辑器内单步撤销，安全措施全部复用。
- **停止不改正文**：中途停止时已生成的建议留在问题上，作者可以逐条看过再采纳。
- **用发现问题时的模型**：与检查保持一致；该模型配置删除后用这类检查的默认模型。
- 不另设任务类型、不进任务队列：单条请求很短，作者在面板里等待结果；批量时前端并发 3 条并显示进度。代价是没有任务级的用量统计（用量写日志）。
