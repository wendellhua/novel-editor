# ADR-001：架构风格——本地模块化单体
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 场景：单人在本机使用；单人维护、AI 辅助开发。
- 平台：Windows 和 macOS 都要支持。
- 界面：用户建议用「Node.js + 本地浏览器」实现。
- 质量优先级：不丢稿 > 易用。

## 候选选项 (Options)
1. **本地模块化单体：一个 Node 服务进程 + 浏览器 SPA**
   - 优点：最简单；浏览器负责渲染和输入法；服务端统一管理文件、数据库和 API Key。
   - 缺点：需要处理端口、单实例和本地访问鉴权。
2. **Electron 桌面应用**
   - 优点：有原生窗口，体验好。
   - 缺点：安装包 150 MB 以上；用户已选择浏览器形态。
3. **纯前端 PWA（数据存在 IndexedDB 或 OPFS）**
   - 优点：无需安装。
   - 缺点：数据受浏览器存储策略影响，可能被清理；大模型 API Key 会暴露在前端；无法在文件系统层面备份。
4. **多进程或服务拆分（编辑服务 / AI 服务分离）**
   - 优点：可以独立重启。
   - 缺点：单用户场景没有收益，进程间通信复杂度高（YAGNI）。

## 决定 (Decision)
采用选项 1：单个 Node 进程，内部按 `system / http / storage / manuscript / bible / llm / skills / checks` 分模块，前端是 Vue SPA。

## 理由 (Rationale)
- 浏览器加本地服务，既满足用户指定的形态，又让数据落在本地文件系统，便于备份和防丢稿。
- API Key 只保存在服务端，前端无法读取。
- 模块边界和依赖方向（见 ARCHITECTURE §3.2）保证以后可以演进，但现在不付分布式的代价。

## 后果 (Consequences)
- **正面**
  - 部署形态简单。
  - AI 任务在服务端执行：关闭浏览器标签后任务仍在运行，重开页面即可看到进度。
- **负面 / 代价**
  - 需要自己处理端口冲突、单实例和本地 HTTP 鉴权（见 ADR-010）。
  - 浏览器草稿和 origin 绑定，所以端口要尽量固定（INV-15）。
