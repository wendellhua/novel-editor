# ADR-004：防丢稿策略——三层保存 + 乐观锁 + 删除可恢复
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 「不丢稿」是质量属性中优先级最高的一项。
- 可能导致丢稿的情况：
  - 浏览器崩溃，或页面被关闭；
  - 服务进程被杀，或机器掉电；
  - 同一章在两个标签页里同时编辑，后保存的覆盖先保存的；
  - AI 一键修正改错了内容；
  - 误删。

## 候选选项 (Options)
1. **只在服务端定时保存**
   - 缺点：浏览器与服务之间的这段时间窗口内，内容会丢失。
2. **三层保护：浏览器草稿 + 服务端事务保存 + 版本快照**
   - 优点：覆盖上面所有情况。
   - 缺点：需要处理冲突和草稿恢复。
3. **每次按键都保存**
   - 缺点：请求过多，并且没有解决多标签页冲突。

## 决定 (Decision)
采用选项 2，具体参数见 ARCHITECTURE §3.3 F2：

| 层 | 内容 |
|---|---|
| L1 浏览器草稿 | 内容变化后防抖 300 ms，写入 IndexedDB 草稿 |
| L2 服务端保存 | 停止输入 1.5 s 后，或连续输入时最长每 10 s，向服务端保存一次；通过事务写入，并用 `rev` 乐观锁，冲突时返回 409，由用户选择保留哪一份 |
| L3 版本与备份 | 每 10 分钟最多一条自动版本，每章保留 30 条；手动版本和修正前版本不会被自动清理；每部作品每天一次整库备份，保留 7 份 |

删除规则：
- 分卷、章节：软删除，可从回收站恢复。
- 作品：只把文件移到 `trash/`，不真正删除。
- 彻底删除：只能由用户在回收站中手动执行。

## 理由 (Rationale)
- 浏览器侧的问题由 L1 兜底，进程或掉电由 L2 的事务兜底，AI 改错或人为改错由 L3 兜底，多标签页覆盖由乐观锁兜底。这样每一种丢稿情况都有对应的保护层。
- 修正和恢复前的快照，与正文更新写在同一个事务里（INV-6），不会出现「改了正文、快照却没写上」的情况。

## 后果 (Consequences)
- **正面**：每一种丢稿情况都有可测试的保护措施；冒烟测试包含「强杀进程后重启，内容完好」。
- **负面 / 代价**
  - 前端需要实现草稿恢复和冲突对比界面。
  - IndexedDB 草稿与浏览器 origin 绑定，所以端口要固定（INV-15）；更换浏览器后，之前的草稿不会带过去。
  - 版本表会增加库体积：每章最多 30 条 auto，加上数量不限的 manual 和 before_fix。
