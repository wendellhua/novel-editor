# ADR-011：创作辅助（AI 味检测、灵感胶囊、智能扩写）与剧情记忆

- 状态：已采纳（2026-10-13，交付后迭代）
- 相关：ADR-006（AI 检查流程）、ADR-007（大模型接入）、ADR-008（Skills）、ADR-009（设定库）、ARCHITECTURE F6 / F7

## 背景

用户反馈要在「AI 检查」中加三个子功能：

1. **灵感胶囊**：根据作品设定、基调、当前剧情与情绪曲线给出五条剧情发展路线，以报告形式阅读；
2. **AI 味一键检测**：找出文本中的 AI 味并支持一键优化；
3. **智能扩写**：每次只根据前文完成当前章节，不能连续扩写多章。

同时要为每部作品**自动**维护「剧情记忆」：每写满 3000 字由 AI 增量更新，历史章节不重复生成（节省 token），让写作中后期的检查、灵感与扩写基于已有剧情，而不是凭空推断。剧情记忆要能查阅。

## 决定

### 一、四个新任务类型，全部走统一的任务引擎

`ai_flavor`、`inspiration`、`expand`、`memory` 都是 `JobType`，复用 F3 的规划、并发、暂停 / 恢复 / 失败重试、用量统计、SSE 进度与单元原子提交。每种类型一个内置技能（`ai-flavor-check`、`inspiration-capsule`、`smart-expand`、`plot-memory`），格式要求仍由 ① 编辑器协议固定。

- 不另造执行通道：剧情记忆要在后台长期运行、断网后能恢复，扩写可能要几十秒，任务引擎已经解决了这些问题。
- `memory` 是**系统任务**（`AUTO_JOB_TYPES`）：检查面板不列出、`POST W/jobs` 拒绝、「AI 检查」上的运行数不计入。
- `inspiration`、`expand` **只能针对当前章节**（`CHAPTER_SCOPE_JOB_TYPES`），只有一个 main 单元，⑥ 取本章结尾（`tailRange`）；本章可以为空（新章节从头写），但本章与前文不能都没有正文。

### 二、模型只产出建议，正文仍只经已有的写入口

- **AI 味检测**的结果是带改写的问题（`ai_flavor` 类），「一键优化」就是 F4 一键修正：先保存、存修正前版本、编辑器内可撤销。本地过滤与 INV-10 同理——改写不能丢掉 target 中的设定库专名、不能过长。
- **灵感胶囊**只写报告（`job_report`），渲染方式与审稿报告相同（结构化 Markdown，文本节点输出），不碰正文。
- **智能扩写**的结果先存入 `expansion`，作者预览后才「插入到章末」，经 `Manuscript.fixChapterBody(…, 'before_expand')` 写入（新增版本原因「AI 扩写前」，不能重复插入；扩写后本章改动过要确认）。
- **「不能连续扩写多章」**由三层保证：范围只能是一章；协议要求只写当前章、不写章节标题；本地整理遇到下一章的标题就截断、篇幅不超过目标两倍。

### 三、剧情记忆：增量、串行、快照

- **触发**：正文保存后防抖 3 秒检查尚未纳入的字数，满 3000 字自动创建任务；超过 30000 字（如第一次给已有的长篇建立记忆）不自动开始，由作者手动开始，避免意外的大额用量；没有可用模型时不更新。后加的任务类型没有单独设置默认模型时沿用相近任务的（`LLM_DEFAULT_FALLBACKS`：剧情记忆沿用章节摘要或编辑审稿），升级后的旧配置不用逐项设置。
- **增量**：每章记录已纳入的位置和末尾 32 个字的锚点。之后只把接续位置之后的正文发给模型；已纳入部分被改过时按锚点找回接续位置，**不会重新发送**。代价：已纳入部分的大段改写不会自动反映到剧情记忆中——提供「重建」。
- **执行**：批次在单元**执行时**才按当前正文选定（创建任务后接着写的内容也能纳入），批次之间串行（每次更新都基于上一次的结果）；每次更新存一条记录：本批的事件 + 更新后的**全书状态快照**（主线进展、人物现状、未解决的冲突与伏笔、情绪走势）。
- **使用**：检查某一章时，取「已纳入章节全部在本章之前」的最后一个快照——检查较早的章节时不会把后文的发展当成前情；审稿与一致性检查不含本章自己（本章写到的不算前情），灵感与扩写可以包含本章已写的部分。剧情记忆放在 ④ 前情提要中，比章节摘要晚裁剪。

### 四、schema v2

`job.type`、`issue.category`、`chapter_revision.reason` 的 CHECK 约束只能通过重建表修改。迁移框架新增 `rebuildsTables`：事务外关闭外键、提交前 `foreign_key_check`、结束后恢复——否则删除旧 `job` 表会级联删掉单元、问题与报告（测试中已用变异验证）。

## 备选方案与取舍

- **剧情记忆按章生成摘要再汇总**：已有章节摘要缓存，但它按正文版本整章重算，长章节写到一半反复保存会反复发送整章；且「每 3000 字」的节奏与章节边界无关。按字数增量 + 锚点更贴合需求。
- **每次更新都把全部历史事件发给模型**：越写越贵。改为只发送上一次的状态快照（几千字以内）与上次的事件。
- **只保留最新状态**：检查较早的章节时会把后文当成前情。保存每次更新后的快照，按位置选用。
- **扩写直接写入正文**：违背 ADR-006「模型只给建议」；作者需要先看再决定。
- **扩写不经任务引擎、前端直接调用**：几十秒的请求无法暂停、断网无法恢复、用量不统计。

## 后果

- 正文保存后多一次防抖检查（读取全部正文计算待纳入字数，3000 章约 10 ms 量级，不在保存路径上）。
- 剧情记忆的质量取决于模型；它只作为 ④ 前情参考，矛盾判断仍要有依据（一致性协议不变）。
- 已纳入部分被大幅改写后剧情记忆可能过时，需要作者「重建」（会重新消耗 token）。
