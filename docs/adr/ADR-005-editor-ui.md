# ADR-005：编辑器与前端——CodeMirror 6 纯文本 + Vue 3 + Naive UI
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 正文类型：网文正文是纯文本段落，不需要富文本排版。
- 规模：单章可能达到数万字，编辑器需要流畅、中文输入法稳定。
- AI 结果展示：需要在正文里高亮问题，点击问题后跳转到对应位置；一键修正后，问题位置要跟着文字变化自动调整（位置映射）。
- 风险：Windows 上 Chromium 149.x 的 contenteditable 有回归，首次 IME 组合输入会丢失（F10，单一来源）。

## 候选选项 (Options)
1. **CodeMirror 6**
   - 优点：只渲染视口内的内容；`Decoration` 和事务位置映射是原生能力；MIT 许可，体积小。
   - 缺点：定位是代码编辑器，需要自己调成「段落 + 首行缩进」的写作样式。
2. **Tiptap / ProseMirror**
   - 优点：富文本能力强，Decoration 也很强。
   - 缺点：引入了富文本模型，本项目用不上，复杂度和体积都更高。
3. **Lexical**
   - 优点：性能路线。
   - 缺点：与 React 绑定更深，生态还在演进。
4. **原生 textarea**
   - 优点：最简单，输入法最稳。
   - 缺点：无法在正文内做高亮。

## 决定 (Decision)
- **编辑器**：CodeMirror 6，只用 `state`、`view`、`commands` 三个包。
  - 开启 `EditorView.lineWrapping`；每个段落占一个逻辑行；可选首行缩进主题；不显示行号。
  - 问题高亮：用 `StateField<DecorationSet>` 实现，随事务自动映射位置。
- **前端框架**：Vue 3 + Pinia + Vue Router + Naive UI（目录树拖拽、对话框、表单都用它）。
- **IME 兜底**：在 S4 的编辑器任务中，必须在 Windows 上测试微软拼音和搜狗/QQ 拼音，在 Mac 上测试系统自带拼音。
  - 测试内容：连续输入、中文标点、候选词上屏、撤销。
  - 如果确认受 Chromium 回归影响，就在 UI 中检测浏览器版本并提示用户；必要时提供 textarea 降级模式（只编辑，不高亮）。

## 理由 (Rationale)
- 纯文本模型和小说正文一一对应，问题的 UTF-16 偏移量可以直接映射到编辑器位置（与 §6 的约定一致），没有富文本到纯文本的转换误差。
- 视口渲染保证长章节的性能。

## 后果 (Consequences)
- **正面**：模型简单；修正操作就是一次 `changes`，撤销栈天然包含 AI 修正。
- **负面 / 代价**
  - 不支持粗体、斜体等富文本。
  - 需要自己编写写作样式主题。
  - IME 风险需要实测确认。

## 实施记录（2026-10-09，T9）
- **textarea 降级模式已直接提供**（编辑器右上角「纯文本」开关），不等确认回归再做：保存、草稿、冲突逻辑与 CodeMirror 模式完全相同，只是没有问题高亮。选择记在 `localStorage`。
- **自动化验证**：浏览器冒烟用 CDP `Input.imeSetComposition` 模拟组字（`n` → `ni` → … → `ni hao`）再上屏「你好」，在 Chrome 150（Windows）下正文逐字正确、自动保存一致；5 万字章节输入到渲染中位数 16.6 ms。
- **仍待人工验证**：CDP 模拟不经过系统输入法，不能替代真实输入法测试。微软拼音、搜狗/QQ 拼音、Mac 系统拼音的实测由用户执行；若复现 F10 中的首次组字丢失，再加浏览器版本检测与提示。
