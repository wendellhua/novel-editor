# ADR-007：大模型接入——OpenAI 兼容 chat/completions，结构化输出三档降级
- **状态**：已采纳
- **日期**：2026-10-09

## 背景 (Context)
- 接入范围：用户只要求 OpenAI 兼容接口，包括 DeepSeek、通义千问、Kimi、智谱、混元和 OpenAI。
- 各厂商结构化输出能力不一致（F8）：
  - DeepSeek 只支持 `json_object`，并且有时会返回空 content；
  - 千问只有部分模型支持 `json_schema strict`；
  - `json_object` 模式要求提示词中必须出现 "json" 字样。
- 思考类模型会额外返回 `reasoning_content` 字段。

## 候选选项 (Options)
1. **引入官方 `openai` SDK**
   - 优点：类型完善。
   - 缺点：需要额外依赖；兼容厂商的非标准字段仍然要自己处理。
2. **使用原生 `fetch` 加轻量客户端**
   - 优点：没有依赖，完全掌控重试和降级逻辑。
   - 缺点：需要自己维护请求格式。
3. **使用 Vercel AI SDK 等多厂商抽象层**
   - 缺点：依赖重；用户只需要 OpenAI 兼容这一种协议。

## 决定 (Decision)
采用选项 2，细节见 ARCHITECTURE §7.3。
- 接口：只使用 `POST {baseUrl}/chat/completions`，非流式。
- 能力档位：每个模型配置一个 `jsonMode`，取值为 `json_schema`、`json_object` 或 `prompt`。
  - 点击「测试连接」时，按上面的顺序依次探测，并把结果写回配置。
- 校验：无论哪一档，返回结果一律用 Ajv 按 Schema 校验（INV-11）。
- 重试：
  - 返回为空、被截断（`finish_reason=length`）、429 或 5xx 时，最多重试 3 次，间隔指数退避；
  - Schema 校验失败时，把错误信息发回模型修复，只修复 1 次。
- 并发与扩展：
  - 每个模型配置有独立的 `maxConcurrency` 信号量；
  - `extraBody` 会原样透传，用来设置 `enable_thinking: false` 等厂商私有参数。
- 内置预设：DeepSeek、阿里云百炼、Kimi、智谱、腾讯混元、OpenAI，以及本地 OpenAI 兼容服务（Ollama 或 LM Studio）。预设只预填 `baseUrl`，模型名由用户填写。

## 理由 (Rationale)
- 以「最差的能力档位也能正常工作，好的档位用得更稳」为原则，在不同厂商之间都能得到同样可靠的结构化结果。
- 不引入依赖，单文件打包更稳。

## 后果 (Consequences)
- **正面**
  - 可以接入任意兼容 OpenAI 的服务，包括本地 Ollama。
  - 换厂商时不需要改代码。
- **负面 / 代价**
  - 预设里的 `baseUrl` 可能随厂商调整而失效，需要随版本更新维护。
  - v1 不做流式输出，界面上的进度按执行单元计算，而不是逐字显示。
  - API Key 以明文保存在本机用户目录的 `llm.json` 中。这是单用户本地场景下可以接受的取舍，日志和接口响应中的 Key 都会脱敏。

## 实施补充（2026-10-09，T10）

不改变上述决定，只记录实施中确定的细节（完整约定见 ARCHITECTURE §7.3）：
- **探测的错误分类**：只有 400 / 422、非 chat/completions 响应、输出不合格才视为「该档不支持」并降级；Key 无效、地址错误、限流、超时、网络错误与档位无关，立即结束。否则一次限流就可能把能力档位错降到 `prompt`。
- **Key 只发给它所属的服务**：修改配置时 `baseUrl` 的 origin 变了而没有提供新 Key，旧 Key 被清空；请求不跟随重定向。避免作者换用其他服务（或填错地址）时把原厂商的 Key 发出去。
- **并发名额覆盖重试等待**：一次结构化调用（含退避等待）只占一个名额，限流时整体放慢，而不是让其他单元继续涌上去。
- **`extraBody` 的删除语义**：值为 `null` 表示从请求体中去掉该字段，用于不接受 `max_tokens` 或 `temperature` 的模型。
- **预设只在服务端**：经接口下发，前端产物保持不含任何外部地址（§6.5 构建扫描）。

## 补充 2（2026-10-15，交付后修复：模型状态与异常处理）

背景（用户反馈）：模型实际连不通时，页面右上角仍显示「已连接」，「测试连接」一直停在「测试中」。排查结论：
1. 右上角的标签是页面与**本机服务**的 SSE 连接，与模型无关，但写成了「已连接」，容易被当成模型状态；模型本身没有任何状态显示。
2. 测试连接与 AI 任务共用并发信号量：任务的请求卡在超时上（默认 180 s，超时还会重试 3 次，一个单元最多十几分钟）时，测试要排在后面等；测试自己的请求也用 180 s 超时；前端没有时限也不能取消。
3. 运行中修改了 Key 或地址，进行中的任务仍用旧配置继续重试。

决定：
- **运行状态**：客户端记录每个模型配置最近一次请求的结果（只在内存），区分「服务不可用」（连接、鉴权、额度、地址、超时、限流、5xx）与「这次请求的内容有问题」（输出不合格、截断、空内容、400 / 413 / 422，不改变状态），附按错误类型的处理建议；连同进行中 / 排队 / 重试数经接口与 SSE 推送。顶栏标签改为「本地服务已连接」并说明含义。
- **测试连接是诊断，不排队**：不占任务的并发名额（多出的这一个请求可以接受），单次请求 ≤ 60 s、整体 ≤ 120 s，客户端断开即中止；界面显示已等待的秒数并可取消。
- **超时只重试 1 次**：超时的重试代价是再等一个完整的 `timeoutMs`；网络错误、429、5xx 等仍重试 3 次。
- **修改配置后按新配置重发**：同一模型配置的请求共用一个可中止的「代」；连接配置变了（或模型异常且有请求卡住时改了其他参数），中止这一代的全部请求，任务的单元保持待执行、每次执行读取最新配置，所以立即按新配置重新发送。代价：被中止的请求可能已产生少量用量。
